# 第一部分：技術調研

**TL;DR**：這個問題本質上比能力①（板子六軸姿態）更難，因為線材是可變形、可交叉、顏色不可靠的細長物體。但如果把範圍限定在「兩端都落在 UNO Q 排針上」的線（v1），這其實是一個相對成熟、可用純古典 CV（HSV 分色＋骨架化＋骨架圖追蹤＋吸附到已知排針座標）解決的問題，因為能力①已經把「開放空間座標」問題轉成了「離散候選點」問題。麵包板孔洞端點辨識則是完全不同、目前專案裡不存在的子問題，**不建議放進 v1**——不是因為做不到，而是因為它需要一套新的幾何偵測（不是重用 ORB/SIFT 特徵比對，麵包板紋理太重複），值得獨立立項。VLM 輔助對「線材路徑追蹤/歧義消解」這個子任務有直接、強力的負面實證（見下方 §5），比原本能力①拒絕 VLM 的理由更站得住腳，不建議採用；訓練模型則是誠實地「可以但暫不建議」。

## 0. 現有基礎

- 每個排針都已經有**即時、被追蹤、經過濾波的像素座標**（`{id, x, y, c, v}`），最高 30Hz 透過 `/ws/detections` 發布。這塊板子的腳距是 2.54mm，換算到 1280×720 的即時畫面，在典型 demo 距離下約落在 **15–30 px**——跟原始 CV 設計文件裡「為什麼拒絕 VLM 做即時逐腳定位」引用的同一個數量級。這個數字在下面 §2c 會反覆用到，是「吸附到已知腳位」信心度的關鎖常數。
- 能力①真正用的技術是 ORB（+ 備援 SIFT）特徵比對真實參考照片、RANSAC 單應性、solvePnP + LK 光流追蹤、One-Euro 濾波——全程零訓練資料，之所以行得通，是因為 UNO Q 的絲印/元件/文字給了 ORB 大量獨特、不重複的紋理。
- 接線驗證架構文件裡的 `vision_presence.py` 明確只做「已知腳位座標上的像素遮擋判斷」，不是線材辨識，且該文件 §9 明確把「完整麵包板網格＋線材端點追蹤」列為刻意不深入設計的第四階段擴充點——本次調研與設計正是要填這個坑。

## 1. 業界先例——別人怎麼做、做得怎樣

- **麵包板轉電路圖的業餘專案**（如 Breadboard Bakery）：灰階→模糊→去斜→網格結構偵測孔洞、輪廓偵測晶片、用最小/最大寬高限制區分線材與孔洞。他們自己的紀錄很坦白：「程式會把線材的一部分，或麵包板的孔洞本身，誤判成線材」——這正是本次設計要處理的線材/孔洞混淆問題，是真實踩過的坑，不是假設。沒有回報準確率數字，明確不處理電阻等其他元件。
- **PCB 走線分割**（比麵包板成熟的學術領域，因為印刷電路走線是平的、不可變形，本質比自由懸空的 3D 杜邦線容易）：即使是這種較簡單的情況，論文作者也判斷純古典分割不夠用，需要訓練 DCNN——但這反過來說明我們的線材比 PCB 銅箔更粗、對比度更高、通常有顏色，是更友善的分割對象。
- **機器人線束組裝的電腦視覺文獻**（跟本問題幾何最像的先例）：對稀疏、單條線材的情況，業界收斂到同一套古典管線：**閾值分割→形態學清理→細化成 1px 骨架→骨架圖分析**——這正是下面 §2 建議的管線形狀，不是我們發明的，是這個領域的預設做法。
- **密集交纏的情況有真正的學習式最先進技術**（HANDLOOM，Berkeley AUTOLAB 2023）：能追蹤穿過 25 個以上交叉點的纜線，但需要 3 萬張模擬影像＋568 張真實標註影像才做到，追蹤準確率 80%、完整解纏準確率只有 64%，而且是為長而軟的纜線/繩子/軟管設計，不是短而半剛性、兩端有塑膠接頭的杜邦線。誠實地讀：這是「線材到處纏繞」情境的天花板技術，需要真實標註資料集才能達到，這正是**不該在 v1 嘗試解決完全通用纏繞情況**的理由。

## 2. 古典（免訓練）技術評估

### 2a. HSV 分色 → 骨架化 → 骨架圖追蹤

**管線**：每幀對 9 種慣用線色（紅/黑/黃/綠/藍/白/橘/紫/灰）各自用 `cv2.inRange` 分色（跟現有 pipeline 判斷深藍色 PCB 的手法同一個套路）→ 開運算/閉運算清理雜訊、補小縫隙 → 細化成 1px 骨架（`cv2.ximgproc.thinning`，古典 Guo-Hall 演算法，免訓練）→ 骨架建圖（度數 1 的像素=候選端點，度數≥3=交叉點）→ 逐分支追蹤。

**能處理交叉/重疊的線嗎？** 部分可以，要老實講：在真正的交叉點，骨架化會產生一個度數 4 的交叉節點，**在單一像素上沒有任何顏色或純 2D 幾何資訊能告訴你哪條進來的分支接哪條出去的分支**——這跟 HANDLOOM 論文要用學習式交叉分類器解決的是同一種根本歧義。唯一有效的古典啟發式是**最小曲率延續**：在交叉點，選切線方向變化最小的那條分支延續下去（線材通常不會在不是自己的交叉點上急轉彎）。這通常對的，但不保證——**建議：使用它，但只要 trace 經過交叉點就標記整條線為 `ambiguous`/低信心**，直接沿用接線驗證架構已經建立的「誠實標記不確定，不要假裝確定」慣例（`stale`、`not_testable`）。

**能處理低飽和度的線色（白/灰/黑）嗎？** 不行——這是色調分色法真實存在、不是假設的盲點，需要不同的備援線索而不是「放寬飽和度閾值」：(1) 邊緣/梯度偵測，利用線材絕緣層固定寬度（~2-3mm）形成「兩條固定間距的平行邊」這個形狀先驗；(2) 高光偵測，PVC 絕緣層在多數室內燈光下會有一條細亮的反光帶。兩者都比色調分色在雜亂桌面背景下更吵。**誠實預期：白/灰/黑線的召回率會明顯低於彩色線，這件事要透過信心值明講出來，不能悄悄漏掉。**

### 2b. Hough 變換/曲線擬合

單純的機率式 Hough 直線偵測不適合當主力——杜邦線常常在插入處有直角彎折，很少整條是一段直線。Hough 比較適合當輔助：在骨架上跑（不是原始影像）把被閾值化打斷的小碎片合併回連續分段；或當交叉檢驗，跟色彩分割結果不一致時降低信心。對彎折本身，用輕量分段線性或低階曲線擬合沿骨架走，不用假設任何一段是直線。

### 2c. 端點吸附到已知排針——這是讓 v1 可行的關鍵洞察

這是整份調研最重要的實務洞察，repo 裡的真實數字直接支持它：把線材端點解析到**任意開放空間座標**很難（那是麵包板孔洞網格這個完全不同的問題，延後到 v2）。但解析到**一個已知、稀疏、離散集合裡最近的成員**——能力①已經即時追蹤好的 32 個排針座標——是完全不同、容易得多的問題：

- 這塊板腳距 2.54mm ≈ 典型 demo 相機距離下的 **15–30 px**
- 偵測到的線材端點只要落在約**半個腳距（≈8–15px）**內就能無歧義吸附——超過這個半徑才開始有跟鄰近腳位打結的風險
- 骨架終端節點的像素級定位誤差通常只有幾個像素，不是幾十個——這比姿態追蹤需要的次像素精度寬鬆得多，是乾淨色彩分割區塊在高對比板面上能穩定達到的水準
- 結論：**吸附到已知腳位的信心應該很高**——前提是候選集合真的是離散且稀疏的。這正是為什麼「只做排針對排針」這個 v1 範圍不是偷懶，而是整個問題裡唯一一種「每個候選端點位置都已知、已追蹤、次腳距精度」的情況，是從能力①免費繼承來的。

## 3. 麵包板孔洞網格偵測——跟能力①的板子偵測比，難還是易？

**用能力①實際用的技術來說更難，但用它沒用到的另一種技術來說反而容易。** 這點需要精確講清楚：**不要重用 ORB/SIFT 參考圖比對做麵包板**——它在麵包板上大概率表現得比在 UNO Q 上更差，不是差不多。原因是特徵比對面對重複性/週期性紋理的經典失效模式：麵包板視覺上幾乎是教科書級的最壞案例——一個幾乎沒有獨特局部紋理的規則孔洞網格，正好是 SIFT/ORB 描述子會局部模糊、單應性估計會退化的條件。UNO Q 的絲印文字、接頭形狀、元件輪廓正是 ORB/SIFT 需要的那種不對稱、局部獨特的紋理，麵包板結構上就缺乏這種東西。

**該用什麼取代**：麵包板是**標準化、公開的幾何**，不是需要從參考照片學習的未知形狀——跟 UNO Q（必須校正的特定板子，佈局不是公開標準）根本不同的起點。幾何管線：(1) 偵測麵包板的矩形外框（顏色/輪廓為基礎，多數麵包板是白/米色/透明塑膠，跟桌面對比明顯，或用印刷的紅/藍電源軌條紋當強力、非重複的顏色線索）；(2) 用已知的標準拓樸（0.1"＝2.54mm 間距、標準行列佈局、標準電源軌位置）從偵測到的四個角**用算術生成**孔洞座標，不用逐孔獨立偵測；(3) 可選：用局部小範圍搜尋（不是全域）做確認/修正。這其實直接呼應能力①已經在用的手法——`POST /api/calibrate` 把板子外框當成使用者對齊過的既定真值（點四個角），不是要 CV 盲猜——同樣的招式對麵包板至少一樣好用，甚至更好，因為麵包板邊緣對比度比 UNO Q 板子更低。

**要放進 v1 嗎？不——這是明確的建議，不是佔位藉口。** 三個理由：(1) 這是一個真正獨立的子系統（新座標系、新校正對齊 UX、新的「這片麵包板孔洞佈局」profile 資料），不是線材追蹤上的小補丁；(2) 使用者實際要的線材辨識能力，限定在「板端排針↔板端排針」範圍就已經完整可展示、有真實用途——因為這兩端座標都已經從能力①免費取得；(3) 真實的示範接線（如已設計的 HC-SR04 電路）本身很常就是排針對排針或排針對麵包板，即使只做排針子集，也已經是「有、能看到、不裝懂」的真能力，而麵包板端點目前明講「偵測到但無法解析」是誠實的已知限制，不是隱藏的缺口。

## 4. 訓練模型的替代方案——誠實評估，不是反射性拒絕

X 光導管分割（用輕量 U-Net + 合成資料）是結構上很接近的類比案例（細長、可變形、曲線狀前景物體 vs 多變背景，想要清晰中心線）。那份研究需要 **9000 張合成影像**，把 U-Net 參數從 1410 萬砍到 68.8 萬才達到 ~71ms/幀，即使如此，真實影像上的 Dice 分數也只有**最佳情況 0.55，較難情境掉到 0.17–0.26**——而且**沒有合成資料預訓練時，純真實資料訓練直接崩到 Dice ~0.1**。兩個誠實的結論：合成預訓練確實有幫助拉近 sim2real 落差，**但**即使做得好也不會到「解決了」的程度，只會到「比什麼都不做好一些，難的情況仍然弱」。另外，一個專門的線材實例分割資料集（WireSeg-36k）之所以存在，正是因為「細長、可變形、雜亂場景裡的物體很難標註，大規模標註資料稀缺」——連取得訓練資料本身都不容易，不只是建模端的問題。

**建議：v1 不做這個**——古典管線更簡單、上線更快、零資料集成本，而且守住專案一開始選定的免訓練/CPU-only/離線可用紀律，原因跟當初選這個紀律一樣（這麼新的板子沒有現成資料集，杜邦線辨識同樣沒有）。**但留一個介面縫**：`BoardDetector` Protocol 的 mock/pipeline 二選一模式就是現成的範本——如果 v2 真的需要（例如密集交纏場景讓古典方法撞到天花板，跟 HANDLOOM 論文轉向學習式方法是同一個天花板），這個切換點在這個 codebase 裡已有先例，不需要重新設計周邊架構。

## 5. VLM 輔助線材路徑追蹤——證據比預期更強烈地反對

這是調研裡挖到一個**直接、最新、量化**的答案，不是要從一般原則外推。2026 年的論文《VLMs Trace Without Tracking》剛好研究這個確切的子問題——模型在「有相近競爭路徑」的場景中追蹤一條選定路徑——測試對象包含線條追蹤任務、糾纏的纜線、地鐵圖，**以及一個麵包板電路線材追蹤基準測試**（15 張電路圖、107 次線材追蹤查詢）。在那個麵包板基準上：**Claude Sonnet 4.5 得分 6.2%，Qwen3-VL-235B 得分 23.7%，GPT-5.4 得分 44.5%，表現最好的 Gemini3-Flash 也只有 71.0%**——遠遠稱不上一個「有明確地面真值」任務該有的可靠度。每個模型最主要的失敗模式都是論文稱作「相鄰線跳躍」：模型正確地從查詢的線材開始，但追蹤到一半跳到附近一條連到不同麵包板孔位的線——依模型不同，佔各自錯誤的 71–98%。論文自己的診斷是「局部競爭：附近相似的干擾物把模型拉離真正的延續路徑」——而且這個失敗**抵抗了顯而易見的緩解手段**：放大模型規模只帶來有限改善，明確的追蹤指令也無法恢復穩定的路徑跟隨。

對照這個專案原本拒絕 VLM 的理由，這其實是**更強**的拒絕理由。原本板子偵測拒絕 VLM 用的是「座標誤差」論證——精度/延遲問題，理論上換成較慢的單次非同步呼叫可以緩解。但線材路徑追蹤的失敗模式性質不同：不是「座標不準」，是「模型根本搞錯自己在看哪個物件」，還很有自信地錯——「相鄰線跳躍」在結構上正好等同這整個能力最需要處理好的「模糊交叉點/相鄰腳位」場景。放慢、單次、非同步的 VLM 呼叫不會修好一個論文已經證明不主要是速度/延遲問題的失敗模式（明確指令跟放大模型都沒修好）。**建議：不要用 VLM 輔助線材端點/路徑歧義消解，即使只是低頻率的非同步輔助角色**——使用者這次明確問到的子問題，正好是這份新證據顯示 VLM 目前很不擅長的那個問題，而且是結構性原因，不太可能只靠降低呼叫頻率就修好。

值得單獨一提、而不是整個抹殺的窄用途：一個粗略的、非路徑追蹤的問題——「這個畫面裡大概看到幾條線、有沒有什麼明顯沒接好、畫面裡有沒有手」——是分類/計數任務，不是路徑追蹤任務，論文的失敗模式不直接針對它。這是一個可行、低風險的非同步用途（例如「畫面健檢」提示，跟古典管線的輸出並列），但不能取代端點解析，若真要做，應該明確標成「粗略建議資訊」。

## 6. 建議——具體、有範圍、跟現有架構整合

**照這個順序建置，盡量重用現有基礎設施：**

- **v1 — 排針對排針線材辨識（古典、免訓練、最快上線）**：新模組，跟 `vision_presence.py` 同一層級，消費能力①/②已經在讀的 `FrameBus`/`DetectionState`——零新座標系、零新相機/追蹤程式碼。每個 tick（節流，不是每個偵測影格都跑）：9 種慣用線色的 HSV 多色分割＋低飽和度線的邊緣/高光備援 → 形態學清理 → 骨架化 → 骨架圖建構 → 對每一對目前可見的排針，測試骨架終端節點是否吸附到附近（§2c，約 8–15px）且有連續/最小曲率路徑相連 → 輸出 `{pin_a, pin_b, color, confidence, ambiguous}` 候選。明確、誠實地不在 v1 範圍：任何沒吸附到已知排針的端點回報「偵測到線，端點未解析」——不猜、不隱藏。
- **v1.5 — 誠實呈現 `ambiguous`/低信心，分色分開統計召回率**——不要把低飽和度線色的低召回率平均進一個總準確率數字裡，demo 腳本應該刻意選彩色線，白/灰/黑線的限制要明講。
- **v2（獨立立項，非 v1 範圍）— 麵包板孔洞網格幾何，之後把端點吸附範圍推廣到「排針∪麵包板孔洞」的聯集**。用角點導引＋網格算術（§3），不是 ORB/SIFT 參考比對。一旦孔洞座標存在成第二個離散候選集合，v1 的追蹤/吸附演算法不需要改就能直接推廣——這正是接線驗證架構文件 §9 說「這個擴充點填進來時，其他都不用改」的原因。
- **v1 或 v2 都不建議、除非出現真正的逼迫性需求**：訓練式線材分割模型（§4——之後可能有道理，現在不明顯值得打破免訓練紀律，保留介面縫）；VLM 輔助路徑歧義消解（§5——最新直接證據顯示這個子任務目前不適合，不只是延遲取捨的問題）。
- **老實講清楚不會做好的地方**：密集多線交纏（一小塊區域擠 3–4 條以上的線）會被標記 `ambiguous`，不會強行輸出乾淨結果；白/灰/黑線召回率會明顯低於彩色線；線材中段被手遮擋會打斷追蹤連續性，即使兩端都看得到；任何終止在非已知排針/孔洞位置的線材端點，v1 設計上就是回報未解析，不是猜錯。

IET Image Processing 2018（PCB 走線分割）、《機器人化線束組裝電腦視覺應用系統性文獻回顧》arXiv 2309.13744/2309.13745、HANDLOOM (CoRL 2023 / arXiv 2303.08975)、《VLMs Trace Without Tracking》arXiv 2605.15672、《X光透視導管分割：合成資料+輕量U-Net遷移學習》PMC7903142、TGGLinesPlus (arXiv 2403.18038)。

# 第二部分：概念設計

## 1. 範圍決策

**採用：v1 = 排針對排針。涉及麵包板的任何連線延後到獨立的 v2。**

| | 排針↔排針 | 涉及麵包板孔洞的連線 |
|---|---|---|
| 端點候選集合 | 已存在、已即時追蹤、已知信心值——來自能力①的 `DetectionResult.pins`，**零新幾何** | 不存在。麵包板孔洞座標系目前專案裡完全沒有設計過 |
| 需要新偵測技術嗎 | 不需要，沿用管線 snap 到既有 32 個排針座標即可 | 需要，且**不能**沿用 ORB/SIFT（重複紋理失效），需要全新的角點導引+網格算術幾何偵測、新的校正 UX |
| 新資料型別 | 只需 `WireInstance` | 還需要 `BreadboardProfile`（幾何+節點映射，全新 profile family） |
| 能否單獨 demo | 能——HC-SR04 demo circuit 本身多半就是排針接線 | 不能單獨 demo，必須先有麵包板幾何才談得上「resolved」 |
| 與接線驗證現有設計的關係 | 直接填入 `vision_presence.py` 已經預留的 Phase-4 seam | 同一個 seam，但要等 v2 的節點身份圖出現才能真正取代 pixel-patch heuristic |

## 2. Pipeline stages

```
FrameBus.get_latest(newer_than=cursor)   ← 既有；WireTraceWorker 是第4個獨立讀者
   (MJPEG client / VisionWorker / WiringWorker / 現在多一個 WireTraceWorker)
        │
        ▼
DetectionState.get()  ← VisionWorker 已算好 (tracking, pins[]: id,x,y,c,v)
        │ if tracking=="searching": 全 wire → skip
        ▼
Stage A — HSV 分色（9色+低飽和度備援）→ 開運算/閉運算清理
        ▼
Stage B — 骨架化（cv2.ximgproc.thinning，1px 骨架）
        ▼
Stage C — 骨架圖建構（度數1=候選端點，度數≥3=交叉點→最小曲率延續）
        ▼
Stage D — 端點吸附：terminal node 找最近的已知排針（半徑≈8–15px）
          0個候選→floating；恰1個→resolved(pin_id)；>1個(tie)→ambiguous_tie（絕不亂猜）
        ▼
Stage E — WireInstance 組裝 {color, path, endpoint_a, endpoint_b, confidence, ambiguous}
        ▼
WireTraceState.set(...) → publish({"type":"wire_trace", ...}) 走既有 DetectionBroadcaster
        │
        ├─→ 前端 WS client（未來 UI）
        └─→ vision_presence.py 升級路徑（消費 wires[] 補強 pixel-patch probe）
```

**誠實規約**（對齊接線驗證的 `stale`/`not_testable` 慣例）：`endpoint_a`/`endpoint_b` 永遠是三種形狀之一，絕不用猜測填補：
```jsonc
{ "kind": "pin", "pin_id": "D7", "confidence": 0.91 }
{ "kind": "floating", "px": [503.2, 288.9], "confidence": 0.4, "reason": "no_known_candidate_within_radius" }
{ "kind": "ambiguous_tie", "px": [503.2, 288.9], "candidates": ["D7","D8"] }
```
`ambiguous: bool`（整條線層級）代表「trace 過程中經過至少一個交叉點，用了最小曲率啟發式續接，不是幾何保證」——即使兩端都 resolve 到具體 pin，仍要在 UI/AI 回應中降級措辭。

## 3. 資料模型

`backend/app/vision/wire_interface.py`（新檔，peer of `interface.py`）：
```python
EndpointKind = Literal["pin", "floating", "ambiguous_tie"]

@dataclass
class WireEndpoint:
    kind: EndpointKind
    px: tuple[float, float]
    pin_id: str | None = None
    candidates: list[str] = field(default_factory=list)
    confidence: float = 0.0

@dataclass
class WireInstance:
    wire_id: int
    color: str
    path_px: list[tuple[float, float]]
    endpoint_a: WireEndpoint
    endpoint_b: WireEndpoint
    confidence: float
    ambiguous: bool
    crossed_junction_count: int = 0

@dataclass
class WireTraceResult:
    frame_id: int
    ts_ms: float
    board_tracking: Literal["searching", "locked", "stale"]
    wires: list[WireInstance] = field(default_factory=list)
```

WS 新增 `type: "wire_trace"`，延續 `api-contract.md` §2 已明示的擴充點——前端對未知 type 已是「忽略」，純加法。

`BreadboardProfile`（v2 才需要，v1 明確不做，只列形狀給後續立項起點）：
```python
class BreadboardProfile(StrictModel):
    schema_version: str
    breadboard_id: str
    outline_mm: tuple[float, float]
    strip_layout: Literal["standard_830", ...]
    hole_pitch_mm: float = 2.54
    corners_mm: tuple[tuple[float,float], ...]
    # 孔洞座標由 corners_mm + strip_layout 算術生成，不是逐孔偵測
```

## 4. 與現有架構整合

**決策：wire tracing 是新的、獨立執行緒的偵測器（peer of `VisionWorker`），不是把欄位塞進 `DetectionResult`。**

理由：`DetectionResult` 的契約是每 frame <100ms 內回傳——這是姿態追蹤的節奏。Wire tracing（45–90ms/frame，見§5）塞進同一個 `detect()` 呼叫會拖慢它，跟接線驗證架構 §9「拒絕把 WiringWorker 塞進 VisionWorker」是同一個論點的第二次套用。新增 `WireTraceWorker`（新 thread）+ `WireTraceState`（跟 `DetectionState` 同構），作為 `FrameBus` 的第4個獨立讀者。

**與 `vision_presence.py` 的關係：互補，不是取代**（至少 v1 不是）。presence probe 保持快速路徑（每 tick 跑，不變），wire tracing 是較低頻率/on-demand 的「深層」補充。`evaluator.py` 的 `class` taxonomy 新增例如 `wire_endpoint_mismatch`（有線但接到錯的 pin）——直接把「swap TRIG/ECHO」demo 情境從電氣層的判斷升級成視覺層也能講清楚，不改 WS 訊息形狀、不改 AI 介面契約。

## 5. 效能預算（1280×720，CPU 單核估計）

| Stage | 估計 ms | 備註 |
|---|---|---|
| A. HSV×9色+備援+形態學 | ~15–30ms | ROI 裁切（用 outline_px）可壓低 |
| B. 骨架化×9 mask | ~20–40ms 合計 | 多數顏色單幀通常是空的 |
| C. 骨架圖建構+追蹤 | ~5–15ms | |
| D. 端點吸附（暴力最近鄰，32點） | <1ms | |
| **合計** | **≈45–90ms/frame** | 遠超能力①的 <100ms 硬性即時預算 |

**結論：不建議每 frame 跑**，會跟姿態追蹤搶核心。**採用 on-demand 為預設**（接線驗證的 `WiringWorker` 明確需要深層答案時才觸發，如 presence pattern 改變、或 AI 呼叫 verify 時順帶跑），節流頻率只當安全上限，不是常態驅動——比固定低頻率背景跑更省 CPU，也更貼近調研原本的建議。

## 6. 失敗模式對照表（節錄重點）

- **交叉/重疊線**：最小曲率延續猜方向，整條標 `ambiguous`——角度接近時可能猜錯，是已知、被承認的分類器極限
- **白/灰/黑線**：召回率明顯較低，信心值要如實反映，不能跟彩色線的準確率平均掉
- **手指遮擋**：中段斷裂會拆成獨立、無法配對的 floating 端點——寧可回報「看不清楚」也不拼錯
- **端點落在麵包板/畫面外**：v1 明確設計行為，回報 `floating`，不是 bug
- **顏色不是電氣事實**：`color` 欄位只是輔助資訊，文件要明講，避免被 AI/UI 誤用成接線正確性的判斷依據

## 7. Milestones

延續 M0–M7（能力①）、M8–M14（能力②）編號，Wire tracing 定位為**平行、只依賴能力①，不依賴接線驗證整條鏈路**的軌道，編號 **M15–M19**：

- **M15** — 顏色分割+骨架化原型（離線驗證，無 snap 無 WS）。驗收：真實紅色杜邦線（5V↔D7）靜態照片，骨架端點落在正確位置
- **M16** — 端點 snap + `WireInstance` 組裝（仍離線）。驗收：正確輸出 `{color:"red", endpoint_a:{pin_id:"5V"}, endpoint_b:{pin_id:"D7"}}`；線一端故意移到桌面空白處驗證回報 `floating`
- **M17** — `WireTraceWorker` 即時整合（WS `wire_trace` 訊息）。驗收：真實相機插線→WS 收到訊息；拔線→回傳空列表；既有 88 個測試不受影響
- **M18** — 交叉線+多色場景驗證。驗收：兩條刻意交叉的線（紅5V→D7、黑GND→D8）各自顏色/端點正確；銳角交叉時至少一條誠實標 `ambiguous`
- **M19** — 與接線驗證 `vision_presence.py` 整合。驗收：延續 M12 的 HC-SR04 demo，TRIG/ECHO 故意接反，presence probe 看不出差異，但 wire tracing 能明確指出「接錯位置」，AI 回應從「訊號不對」升級成「線接反了」

## 8. 明確拒絕的替代方案

1. **拒絕：塞進 `VisionWorker`/`pose_tracker.py` 同一個 loop** — 45–90ms 會拖慢已上線的姿態追蹤節奏，跟接線驗證架構已經套用過的同一條紀律
2. **拒絕：把結果塞進現有 `DetectionResult.pins`（加 `connected_to` 欄位）** — 假設線只會連兩個已知 pin，一旦要表達 floating/ambiguous_tie 或未來麵包板孔洞就無處安放，獨立型別維持職責邊界跟現有契約一致
3. **拒絕：用 ORB/SIFT 偵測麵包板孔洞網格** — 重複紋理的經典特徵比對失效案例，根本不適合，不是「同一招少做一點」的程度差異
4. **拒絕：VLM 做線材路徑追蹤/端點歧義消解，即使低頻率非同步輔助** — 2026年直接 benchmark 顯示最好的模型也只有 71% 準確率，主要失效模式「相鄰線跳躍」跟本設計要處理的交叉歧義是同一個結構性問題，論文已證明放大模型/更明確指令都修不好
5. **拒絕：訓練輕量分割模型** — 類比案例（導管分割）顯示即使投入大量合成資料，真實影像準確率仍上不去，不值得為此打破免訓練紀律；保留 Protocol 介面縫供未來需要時插入
6. **拒絕：麵包板孔洞偵測跟 v1 排針追蹤合併交付** — 完全不同的技術棧、資料模型、校正 UX，合併只會讓已經有 demo 價值的 v1 被無關的麵包板幾何設計卡住發布時間
