# R1 + Eye 智慧眼鏡 MVP

在 Board Vision 按「智慧眼鏡」即可進入彩色串流。預設為 1920×1080、30 FPS、標準降噪。
解析度與 FPS 由「套用」送出，會短暫重新連線；降噪可立即切換，不重新開啟相機。
「退出」或 Esc 會關閉 Eye，恢復原相機與畫面設定。Eye 沿用接線引導目前的控制板、YOLO 架構與 profile，
可使用 `models/eye/manifest.json` 所列的 Eye 訓練副本；一般相機保留原權重與 session。
辨識流程為 YOLO、GPIO／Pin 平面投影、既有局部腳位影像校正與小幅顯示平滑。
Eye 使用頁面內滿版，不要求瀏覽器原生全螢幕；切換瀏覽器全螢幕不會關掉 Eye，Esc／退出仍恢復原來源。

| 控制 | 選項 |
|---|---|
| 解析度 | 1920×1080、2048×1512、1080×1920、720×1280 |
| FPS | 30、60 |
| 降噪 | 關閉、標準、強 |

設定只保留在目前頁面；首次進入使用 1080p30＋標準降噪，退出後再進入沿用最後成功的 Eye 設定，
失敗的套用不覆蓋已成功設定，重新整理頁面則回到預設。介面分別顯示收到的影像尺寸、
接收 FPS、降噪處理 FPS、YOLO 推論 FPS 及顯示 FPS。60 FPS 是相機要求值，降噪、推論與顯示可能跟不上來源速度。
不把插值放大當成相機實際解析度，也不把錄影模式當成照片解析度。

串流啟動中、切換中或斷線時會隱藏上一個畫面與標記。重新插好眼鏡後可按「套用」重試。
Eye 相機一次由一個程式擷取；使用整合功能時，請關閉獨立 Eye 測試程式。

## 零件與 Pin

沿用 Board Vision「Pin 接線引導」的 YOLO／ONNX、profile 與辨識門檻。
不強制選 Pi 5，也不另外啟用原本停用的辨識器。以下為一般接線引導的原始模型；
Eye 的獨立訓練副本只在眼鏡模式首次進入時載入，退出即切回原 session：

| 目標 | 模型 | 腳位 |
|---|---|---|
| Raspberry Pi 5 | `models/board-pose-pi5-handheld-v2.onnx` | GPIO / J8 |
| HC-SR04 | `models/hc-sr04-corner-pose-v3-robust.onnx` | 4 Pin |
| HW-123 | `models/hw-123-pose.onnx` | 8 Pin |
| MRD-TF240-8P-CS TFT | `models/mrd-tf240-8p-cs-pose.onnx` | 8 Pin |

依使用者最新選擇，Eye 採用 **YOLO + 既有腳位影像校正**：
`EyeYoloWorker` 對同一張原尺寸影格執行板卡及零件模型，將 YOLO 四個有順序的角點
與既有 profile 的腳位座標做平面投影，再以當前影像的 Pi 5 J8 接點列或 TFT 安裝孔做局部校正。
沿用原有投影與局部影像校正架構，不新增 AI 模型；不經 SIFT、多幀共識或光流追蹤。
一般相機仍使用原本接線引導流程，退出 Eye 即恢復。

板卡與各零件模型以平行工作執行同一影格，每個目標每張影格最多做一次 YOLO forward。
Pi 5 漏判後，下一張新影格才輪換到接線引導原有的 `board-pose-pi5.onnx` 全景或局部搜尋，
不執行 reference SIFT。此 Pi 備用模型只提供本體框，**不允許用它的角點輸出 GPIO**；
連續三張找到本體後重試主要模型，以免永遠停留在本體辨識。
Pi 5／TFT 的局部搜尋使用有重疊的直向區域，HC-SR04 使用四區；
命中後繼續對下一張新影格推論該區域，漏判才把搜尋位置移到下一區。
只保留搜尋位置，不保存舊辨識或 GPIO；代價是重新找到目標可能需要數張影格，漏判當幀不顯示舊腳位。
框與角點回算到原影格座標，輸出解析度不變。全部目標完成後才做類別間 NMS 並送出整組結果，
同一組模型不會同時處理第二張影格，避免共用 CUDA 輸入緩衝區互相覆寫。

畫面使用接線引導原有的 `PinOverlay`、`ComponentPinOverlay` 及步驟連線標記：
顯示藍色板框、GPIO／Pin、當前接線目標與篩選高亮。**僅 Eye** 另外使用
`ObjectRecognitionOverlay`，用同一組 YOLO 的新鮮本體結果顯示名稱；尚未取得腳位時，
顯示虛線本體框及「腳位定位中」；Eye 已知被畫面裁切時改顯示「請完整入鏡」。本體框不供腳位計算，也不表示腳位已定位。
Webcam 不建立這層外框／名稱提示，也不以本體結果取代原本的搜尋狀態；即時追蹤開啟與關閉時都保留原來的藍框、GPIO／Pin、接線目標與鏡像／校正設定。
Eye 的鏡頭、降噪與選用的訓練副本會影響輸入，
因此不能保證不同攝影機得到完全相同的辨識結果。
Pi 的 Eye 校正使用 `vision/eye_j8.py`：在當前投影附近尋找兩列接點對比，只做垂直於排針列的共同位移，
保留沿列腳距、兩列間距及腳位編號。舊暗色接頭輪廓會和深色桌墊合併，引起約20px跳動，
因此 Eye 改用接點列；一般 Webcam 的 `_correct_pi5_j8_from_image` 保持原樣。
TFT 沿用安裝孔演算法，取樣保留孔環半徑與模糊邊緣所需像素，避免YOLO框裁掉圓環。
有四孔時依四孔校正；只有三個當幀孔位時，用它們的仿射轉換調整當幀YOLO四角，診斷明列三孔觀測／一角推算。
少於三孔、推算位移超出原搜尋範圍或幾何不成立時保持當幀YOLO；Webcam仍走原四孔流程。
校正不改 YOLO 零件身分，不增加推論次數，不儲存跨幀偏移；影像不足時保留當前投影。
HC／HW 的既有局部校正在本次原型未可靠改善，因此仍使用 YOLO 投影。
腳位出現不代表所有實體腳位編號與對位誤差已驗證；新視角的量測與殘餘誤差見 `runs/eye-fix-20260915/RESUMED.md`。
Eye 不讀取 C920 的相機內參、FOV、曝光、對焦或手動畫面偏移。沒有新增校正、自動對焦、
接線確認或電氣驗證介面；此模式暫停原有接線／驗證背景工作，退出後恢復其執行。

## 串流實作

`backend/app/capture/xreal/` 完整包含 HID 控制、擷取與降噪程式及來源授權。
執行時不需要 `xreal-eye-test` 資料夾、Nebula 灰階服務或另一個 Web 伺服器。

1. 使用 R1 的 USB ID `0B05:1D9D` 定位裝置；需要時透過既有 HID `0xD3 / 45100100` 開啟 Eye UVC。
2. 獨立子程序使用 Windows Media Foundation / OpenCV `CAP_MSMF`，讓 Windows 協商影像格式。
3. 共用記憶體只保留最新 BGR 影格；降噪在原尺寸做空間濾波及帶移動判斷的時間濾波。
4. 同一個降噪影格送入 FrameBus 給模型與畫面使用，預覽 JPEG 品質固定 95。
5. Eye 固定使用 `/api/tracking/frame` 傳送這一輪 YOLO 的同幀影像及標記，
   不受一般相機即時追蹤開關影響。30／60 FPS 是來源要求及顯示上限；
   顯示實際速度依完整一輪 YOLO 的處理速度，不用舊腳位疊新影像。

相機重開會遞增 runtime revision，清除舊影像／追蹤／Pin／降噪歷史，FrameBus 序號保持遞增。
切換 Eye 保留已載入的 ONNX sessions 與原模型設定。一般相機選擇器會跳過 R1 的 DirectShow 開啟探測。

### Eye GPU 降噪與診斷

標準降噪在首張影格才初始化 CuPy CUDA，於原尺寸執行空間濾波及移動區域時間混合；
GPU 與 CPU 使用相同參數，整數捨入可能略有差異。Eye 使用自己的 CUDA stream、記憶體池與歷史影格，
關閉時只釋放自己的資源。CUDA 初始化或處理失敗會改用 CPU，重新建立時間濾波歷史，並回報原因。
關閉降噪維持原始像素，強降噪沿用 CPU 演算法；沒有插值放大或新增判斷模型。
正式 Eye 跳過未使用的全圖移動比例統計及其標量下載，逐像素移動判斷與濾波歷史不變；
1080p／2048×1512的真實CUDA測試確認啟用／停用統計時輸出及歷史緩衝完全相同。
這些降噪及平行搜尋變更只在 Eye 執行，Webcam 的相機參數、辨識與追蹤流程維持原樣。

介面顯示例如 `YOLO CUDA 5/5`，表示列出的五個已載入模型使用 CUDA 後端；
其中可能包含 Pi 5 的替代 YOLO，並不表示每張影格做五次 forward。
CPU、混合與未就緒會分別顯示；滑鼠停在模型狀態可查看各模型實際後端、前處理與回退原因。
降噪另顯示 CUDA、CPU、關閉或初始化中，CPU 回退原因放在其提示文字。
狀態 API 讀取失敗時隱藏舊後端診斷，接收與降噪 FPS 顯示未知；再次讀取成功後恢復。
舊版 API 沒有診斷欄位時不推測 CUDA 狀態。

推論 FPS 是完整同幀 YOLO 組的輸出頻率，`processing_ms` 包含等候各模型與影像封裝，
不是單一模型 forward 時間，也不是各平行模型耗時相加。載入 CUDA 不代表所有算子皆在 GPU，
更不表示辨識或實體 GPIO 對位正確。下方實測保留各自版本與條件，不能當成這次平行／GPU 改版的新 FPS。

### Eye 排程、解碼與傳輸

此 Windows／Python 3.12.4 環境的 `time.monotonic()` 使用約 15.6 ms 精度的 `GetTickCount64`。
Eye 的短等待與擷取／推論排程改用 `perf_counter()` 的 QPC 時鐘，搭配短時間 `sleep`；
離線計時測試中，要求 2 ms 的等待由約 15.5 ms 降至 2.47 ms。這是本機等待時間，並非串流 FPS。
修改只作用於 Eye，沒有調整 Windows 全域計時週期；FrameBus 時間戳、影格年齡與斷線判斷仍沿用
原本的 monotonic 時間域。記錄位於 `runs/eye-performance-20260915/eye-wait-audit.json`。

Eye 額外啟用先依類別分數排除候選的解碼路徑，再交由原有座標、角點及 NMS 解碼器處理。
此解碼最佳化不改變輸入尺寸、信心門檻、候選順序與 NMS 門檻；退出 Eye 即關閉此選項，
一般 Webcam 使用原解碼流程。

Eye 每幀影像與全部辨識只透過 `/api/tracking/frame` 同幀封裝傳送，不再重複發送每個模型的
逐幀 WebSocket 訊息。runtime 事件仍保留；一般相機 worker 的發布設定沒有改動，退出 Eye 後恢復執行。
診斷另列 `bus_wait_ms` 與 `postprocessing_ms`，區分等待影格與結果發布的耗時。

本輪相關後端測試 **174 項通過、1 項跳過**，前端測試 **95 項通過**；
涵蓋時鐘分離、停止與切換、單次推論預算、解碼結果一致及原相機恢復。最終即時 FPS 另以硬體量測確認。

## Eye 模型副本與框穩定

`EyeModelLocator` 僅包住板卡及零件的模型入口。一般模式永遠呼叫原 session，Eye 模式才切到
manifest 指定的獨立 ONNX。兩者都保留以供重入，不在同一影格重複推論。
要求 CUDA 時，無法載入 CUDA 的新副本不會取代原模型，診斷會列出原因。
manifest 在該程序第一次進入 Eye 時讀取；部署新副本後須重啟。
原模型檔、Webcam 相機參數及校正檔不會被此流程寫入。

`EyeYoloDisplayStabilizer` 在類別間 NMS 後對當前辨識做小幅自適應平滑，
同一轉換同步作用於目前的外框與 Pin，不新增判斷模型、光流或未辨識時的預測腳位。
小幅抖動較慢更新，連續平移／旋轉快速跟隨；更換来源、漏辨識與錯誤立即清除歷史。
角點順序翻轉或大跳動會先隱藏該張標記，下一張一致的新觀測才重新顯示。
最大角點校正依物件大小限制為 3–8 像素；這不能修復模型一直輸出錯方向的問題。
若 YOLO 原始本體框或角點已被相機畫面邊界裁切，保留本體名稱但不輸出扭曲的完整 GPIO／Pin；
板子完整進入畫面後，由新的辨識立即恢復腳位。這個檢查只用當前 YOLO 座標，不增加模型。
Eye 名稱使用當前有效的姿態框定位，避免 HC-SR04 過大的原始偵測框把文字拉遠。
名稱定位不改動本體框資料，Webcam 不使用這層 Eye 名稱顯示。

合成静止測試的標準差由 2.13 降至 1.12 像素；327 個舊 Eye 封包重播的座標變動也減少，
但真實移動與辨識誤差混在其中，不作為實體 GPIO 精度證明。
本次模型訓練、現場驗證與限制見 `runs/eye-fix-20260915/RESULTS.md`。

## API

`GET /api/glasses/stream` 讀取狀態與模式。

`PUT /api/glasses/stream` 啟動或更新；完整 JSON：

```json
{"width":1920,"height":1080,"fps":30,"denoise":"clean"}
```

`denoise` 為 `original`、`clean` 或 `strong`。相同相機設定只更新降噪；錯誤後的相同設定會重新連線。
`DELETE /api/glasses/stream` 關閉 Eye 並恢復原來源，重複呼叫不會重開原相機。

三種操作皆回傳 `active`、`state`、`error`、`requested`、`actual`、`capture_fps`、
`processing_fps`、`runtime_revision` 與 `modes`。狀態含 `stopped`、`starting`、`switching`、
`running`、`stopping`、`error`；相機啟動非同步，PUT 後由 GET 讀取實際結果。
`actual` 在收到影格前為 null 值。不可用的解析度、25 FPS 等不支援設定回 HTTP 422。

額外診斷欄位為 `denoise_backend`（`pending`／`cuda`／`cpu`／`none`，未啟動可為 null）、
`denoise_fallback_reason`，以及 `inference`（沒有 Eye worker 時為 null）。`inference` 包含
`processing_fps`、`processing_ms`、`processed_frames`、`error` 與 `models`；各模型含 `id`、
`actual_backend`、`available`，以及可用時的 `preprocessing_backend`、`fallback_reason`。
`available: false` 不計入 CUDA 已就緒數；前端相容缺少這些診斷欄位的舊 API。
