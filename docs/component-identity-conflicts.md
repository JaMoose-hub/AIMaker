# Webcam：TFT 板邊被誤認成 HC-SR04

## 本次原因與範圍（2026-09-17）

同一張實拍只有 Pi 5 與 TFT，但 HC 模型對 TFT 板邊輸出約 0.71 的信心值，
之後光流持續追蹤這個錯誤身分。不同單類別模型的分數不能直接當成同一把尺。

本次不重新訓練、不提高全域門檻、不改接線紀錄、GPIO 定義或智慧眼鏡路徑。
修正的是一般 Webcam 的候選身分與即時顯示，不能視為電氣驗證。

## 修正

- `component_identity.py`：HC 候選的大部分區域（>=70%）落在 TFT 中，且面積
  比例介於 4–65% 時，才進一步檢查。不能只因框重疊就拒絕。
- 從當前像素確認 TFT 的大面積內嵌暗色矩形與兩端藍色板條；同時確認 HC
  沒有既有的雙換能器特徵支持。當前參考特徵匹配已確認 HC 時保留候選。
- 模型 worker 僅使用 200ms 內、非未來、尺寸相同的 TFT 配對來源，並用
  本張影像再次檢查外觀。判定衝突時清掉 HC 的舊定位與連續追蹤狀態。
- 即時 worker 在同幀投影後再檢查一次，並清掉錯誤 HC 的光流模板與短暫
  預測；TFT/Pi 的追蹤不受此清理影響。上游的拒絕也不能被顯示端補回。
- `pose_quality.reason = component_identity_conflict`，另提供
  `identity_check` 的重疊比例、面積比例及外觀證據，原模型分數保留供診斷。

## 驗證

- 18 個相關測試檔：**303 passed**，包含新衝突測試、HC 原有手持/重新取得、
  Pi 電源線修正、光流、預測與 Eye 回歸。非整個 repository 的完整測試。
- 保存本機誤认實拍於已排除 Git 的 `runs/identity-guard-20260917/`，
  作為可重複測試案例；CI 沒有這份本機圖片時會略過該項，仍跑合成測試。
- 該實拍 HC 假框約 88% 與 TFT 重疊，面積約為 TFT 的 18.4%，新規則拒絕。
- 單一保存畫面重跑 100 次，判斷耗時中位數約 1.66ms、P95 約 2.01ms；
  這是該電腦的單幀微量測，非各場景延遲保證。
- 重啟後連續 60 個不同畫面：假 HC 框 **0/60**；TFT/Pi 皆鎖定 **60/60**，
  Pi 均保留 40 個腳位。整包處理中位數 16ms、P95 32ms。
- 依瀏覽器驗證流程查看現有分頁：鏡頭可見、假 HC 四腳標記消失，TFT/Pi
  的藍框仍在；接線紀錄仍為 **10/11**。沒有刷新頁面或重設進度。

## 邊界與後續現場確認

這是针对已證實的「TFT 板邊假 HC」的保守規則，不是通用分類器。
TFT 未定位、亮屏或嚴重遮擋而無法確認暗色面板時不做這項排除，仍可能
存在模型誤認。不能把單一靜止場景的 60 幀結果說成所有場景 100% 準確。

下一次現場只需將真正 HC-SR04 放回 TFT 旁邊，再各自拿起/放回一次，
確認兩者可同時顯示且不互換身分；不需要重新拍攝整套驗收資料。
