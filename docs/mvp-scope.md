# Board Vision MVP 範圍定義

**版本** v1.1（2026-08-01）— 經對抗式審查修正：6 項事實錯誤、3 個漏掉的波次項目、估時 4 週 → 10 週
**定位** AI Maker Studio / AI Maker Runtime（內部提案）能力① 及其延伸的 MVP

---

## 1. 先確定 MVP 的目的

**這個 MVP 的工作不是「可出貨的產品」，是「一個證明概念為真、且團隊做得出來的 demo」。**

| 出貨產品會優先 | 提案 demo 應優先 |
|---|---|
| 功能廣度（多板卡、多元件） | **單一場景做到無可挑剔** |
| 平均正確率 | **零尷尬失敗**——在主管面前打一個錯的勾，比不打勾傷害大得多 |
| 邊角案例覆蓋 | **五分鐘內講完一個完整故事** |
| 效能最佳化 | **每個聲稱都有量測數字支撐** |

推論兩件事：

1. **「說不知道」是功能，不是缺陷。** 會誠實說 `uncertain` 的系統，在工業／教育場景是可信賴性賣點。與本專案既有的 never-guess 紀律同向。
2. **量測數字本身就是提案資產。** 「pin 指派正確率 94%，在真值資料集上量測（n=150 verdict）」比「運作得不錯」有說服力一個數量級。所以量測制度（M33）不是成本，是 deliverable。

## 2. MVP 範圍：五個 demo beat

MVP 的定義就是「這五段能在真實硬體上連續跑完」。**不服務這五段的功能都不在範圍內。**

| # | Beat | 內容 | 現況（經核實） |
|---|---|---|---|
| **1** | **看得懂板子** | 板子入鏡 → 即時標註 32 腳位 → 點腳位顯示能力卡 | ✅ 程式路徑完整（M0–M7），**但一鍵 demo 目前跑 mock**（見 §2.1） |
| **2** | **回答得出問題** | 「哪支腳可以接 servo？」→ PWM 腳位亮起並附中文說明 | ✅ 同上 |
| **3** | **引導接線並判定** ★核心 | 內建 HC-SR04 四步計畫 → 逐步引導 → 插對打勾、插錯點名、證據不足說不確定 | ⚠️ 後端已寫（M22）但**準確率不足**；**前端完全不存在**（見波次 F） |
| **4** | **AI 看得懂現場** | 地端 VLM **按需問答**（「這顆是什麼元件？」）；GPU 機器另可開定時場景旁述 | 📐 已設計（M28），未實作 |
| **5** | **拔網路線照常跑** | 全程無雲端依賴，現場斷網演練 | ✅ 已核實（見 §2.2） |

### 2.1 Beat 1/2 的重要註記（審查修正）

程式路徑成立，但 `config.yaml` 目前是 `source: synthetic` + `detector: mock`，而 `scripts/demo.ps1` **全程不覆寫**——所以「一鍵 demo」現在跑的是合成場景與假偵測器。真管線 `vision/pipeline_detector.py` 可用，切換是 config/env 的事。**這件事屬波次 E 的工作，不能假設已完成。**

能力卡的危險警告也要誠實：`severity: danger` 的措辭只存在 **5 支腳**（AREF、D3、BOOT、A0、A1），其餘 22 支是 `warning`，而 `GND_D`/`IOREF`/`RESET`/`GND_P1`/`GND_P2` 完全沒有 warnings。**Beat 1 的 demo 腳本必須指定點 AREF 或 D3 或 A0/A1**，否則講者會點到一支沒有警告的腳。另：板級「非 5V 容忍」橫幅文案是硬編碼的 locale 字串（只有觸發條件來自 board.json）——「零資料成本上新板卡」在這一點上有例外。

### 2.2 Beat 5 的核實結果

執行期依賴只有 fastapi/uvicorn/opencv/numpy/pydantic/pyyaml/jsonschema；`backend/app` 無任何 requests/httpx/urllib/aiohttp import；前端只有 react/react-dom；favicon 是 data URI；server 綁 127.0.0.1。**聲稱成立，但目前只靠 code review 支撐——波次 E 要補一條自動化測試斷言零外連。**

### 2.3 Beat 3 分三級出貨（審查建議，採納）

這是把 Beat 3 的出貨與精度工作的成敗**解耦**的關鍵設計：

| 級別 | 內容 | 需要什麼 | 可用時機 |
|---|---|---|---|
| **L1** | 只報端點與信心，不下判定 | 今天就有 | 現在 |
| **L2** | `guidance.advance_mode: "confirm"`——**講者按鍵推進**，系統顯示證據但不自動判定 | M26（設計已存在） | 波次 C 後 |
| **L3** | 自動打勾／點名錯腳 | M34 + M35 | 閘門過了才開 |

**demo 腳本以 L2 為預設、L3 為「閘門過了才開」。** 這樣即使精度波次落後，Beat 3 仍然演得出完整故事（講者說「我插好了」按一下，系統顯示它看到的證據）——而不是整段開天窗。

## 3. 明確排除（附理由）

每一項都已有設計文件，屬「已想清楚但這一輪不做」：

| 排除項目 | 理由 |
|---|---|
| **能力② 電氣驗證**（M8–M14） | 需要板端 firmware，一整條新硬體路徑。視覺驗證已能講完故事 |
| **雲端計畫生成**（M27） | 內建範本達到完全相同的 demo 效果。雲端故事**用架構圖講，不用程式講** |
| **多板卡支援** | 一塊 UNO Q 做到無可挑剔 > 三塊都七零八落。校正流程能登錄新板，**演給人看就好** |
| **色相無關 ridge 通道**（M20–M21） | 已實作但實測紫線 recall = 0、RAW 假分支 26 條。誠實說「支援 5 色，經實測」比開一個沒驗證的通道好 |
| **交叉線處理**（M18–M19） | 不處理刻意交叉。**但注意 HC-SR04 四步是累加的**——第 4 步時板上同時有 4 條線，且 re-check 要求每個 tick 所有已完成腳位仍可見。**「4 線同時在場的 re-check 穩定性」必須驗**（波次 C） |
| **進度旁述**（M29） | Beat 4 只做按需問答。砍掉它同時消滅 CPU-only 延遲問題與「AI 說一套、勾打另一套」的機會 |
| **標籤燒錄**（playbook R2） | R5 明寫「錯誤標籤會把準確率打到 0–10%」，而信心閾值目前只有 n=1 錨點。**燒錄等於把可能錯的腳位名以不可質疑的形式餵給模型** |
| **ai_hint 窄縫**（M24） | `GuidanceResult.ai_hint` 目前是死欄位、無寫入點，與此決定一致 |
| **絕對 0.5px 靜態抖動** | 已證實是錯的度量（精度計劃書 L4）。改用 ≤8% pin pitch |

## 4. 完成定義（可量測的閘門）

### 4.1 精度閘門

**分母定義（審查要求）**：所有比率以 **per published verdict**（M35 debounce 之後發布的判定）計算，在 `golden-v2` 資料集的 `recorded` mode 上量測。

**統計功效**：要以 95% 信心宣稱 `≤0.02` 且觀察到零事件，rule of three 需 **n ≥ 150 個 verdict**。`golden-v1`（約 40 frames）是 CI 固定基準，**不足以支撐提案裡引用的數字**——正式數字必須在完整 session（約 225 frames）上量。

| 指標 | 閘門 | 現況 |
|---|---|---|
| **`verdict_dangerous_rate`** ← 唯一 release gate | **≤ 0.01**（波次 B 含 M36） | 未量測 |
| `pin_assignment_accuracy` | ≥ 0.90 | ≈0.3 `[推估]` |
| 靜態 `flips_per_minute` | ≤ 30 | ≫120 `[實測]` |
| `wire_recall`（5 種啟用色） | ≥ 0.85 | ≈0.8 `[推估]`，**且 yellow/green 從未用真線採樣過**（見 §5 採購） |
| `empty_scene_fp_per_frame` | ≤ 0.2 | 未量測 |

### 4.2 體驗閘門

- 冷啟動 → 腳位標註 **< 10 秒**
- L3 模式：插對打勾 **≤ 1.1 秒**；插錯點名 **≤ 2.1 秒**
- **五個 beat 連續跑完 3 次無誤**
- 降級演練：關掉 Ollama → 打勾照常；拔網路線 → 全部照常

### 4.3 誠實性閘門（當 deliverable 驗）

- 故意插兩腳中間 → 回報 `uncertain`，**不是**猜一個
- 線平躺在腳位上不插入 → **不打勾**（M37 未做時回報 `attachment=unknown` 且不打勾）
- 拔掉已完成步驟的線 → 偵測到退回並引導修復
- `verdict_uncertain_rate` **只有上界沒有下界**——不得為了數字好看把不確定硬轉成確定

## 5. 波次與估時（修正後）

**估時經審查修正：純工 ≈40 人日，加 20–25% 餘裕 → 9–11 週，點估 10 週。** 原本的「4 週」低估約 2.5 倍。

| 波次 | 內容 | 服務 | 人日 |
|---|---|---|---|
| **A. 讓 Beat 3 準** | M31 遙測誠實化 (1.5d) → M32 內參標定＋**曝光/WB 管線**＋中灰墊 (2.5d) → **M33 量測制度 (6.5d)** → M34 幾何三修 (5d) | 3 | **15.5d** |
| **B. 讓 Beat 3 穩** | M35 時間層 (4d) → M36 framing 8.4px/mm＋治具 (3.5d) → **golden-v2 重擷 (1d)** | 3 | **8.5d** |
| **C. 多步驟引導** | M25 計畫 schema + **降級版驗證器** (1.5d) → M26 PlanRuntime (2d) → **內建 HC-SR04 計畫資料＋schema (1d)** → **4 線 re-check 與假 regression 實測 (1d)** | 3 | **5.5d** |
| **D. AI 現場層** | M28 VLMWorker + Ollama（**只做按需問答＋文字通道注入**）＋ **Ollama 前置（安裝、`ollama pull qwen3-vl:4b` 3.3GB、VRAM 探測降級）** | 4 | **2d** |
| **F. Beat 3 前端** ← **原文件完全漏掉** | `guidance_check`/`plan_progress` 的 WS 路由與 store、`/api/guidance/*` client、步驟卡（目標腳位＋文案）、4 種 step 狀態、`uncertain`/`paused_regression` 的可操作文案、advisory 與權威判定的視覺區隔、zh-TW/en 字串 | 3 | **4d** |
| **G. drape 閘門**（M37） | G9 四道測試 + `attachment` 欄位 + UI 閘門訊息 | 3 | **2d** |
| **E. Demo 打磨** | 五 beat 腳本、**切真 detector/相機**、**MSMF→dshow 切換與驗證**、`demo.ps1` 前置檢查（相機列舉、px/mm 理智檢查、Ollama 健康檢查、`wire_trace.enabled` 檢查、自動 activate 計畫）、**零外連自動化測試** | 全部 | **2d** |

**合計 39.5 人日 ≈ 10 週（單人，含餘裕）。**

### 5.1 依賴（審查修正）

- **硬性鏈**：M31 → M33 → M34 → M35，順序不可調。時間層若在幾何修好前上線，會把「每 tick 抽籤」變成「穩定地報出抽籤的眾數」——比看得見的抖動更危險。
- **C/D/F 可並行開發，但 C 的驗收必須排在 M35 之後**：M26 的推進規則是「`correct` 連續 2 tick」、re-check 是「已完成腳位連續 2 tick 不在 `occupied_now`」。現況 ≫120 flips/min（2Hz 下每 tick 至少翻一次）→ **M26 的驗收在 M34+M35 之前必然失敗**。開發可以先做，驗收不行。
- **F 不依賴 A/B**：前端消費 WS 訊息與 REST，與判定準確率無關。**應該早做**，因為它是唯一能讓 Beat 3 被看見的東西。
- **M33 是最被低估、也最危險的單項**：6.5d，而且**它的落後不可見**（不產生任何畫面上的東西），但 M34/M35/M36 全部堵在它後面。排程時要當關鍵路徑管。

### 5.2 立刻要下單的採購（前置期不在人日內）

| 項目 | 為什麼是阻塞項 |
|---|---|
| **黃色、綠色杜邦線** | §4.1 的閘門寫「5 種啟用色 recall ≥0.85」，但 yellow/green 的 HSV 頻段**從未用真線採樣過**（程式註解自己說是室內場景猜測）。沒有實體線就無法採樣、也無法量測 |
| 霧面中灰墊（L*≈50） | M32 的一部分。白紙會讓 AE 把 PCB 壓暗 1–1.5 stop，且把陰影對比拉到最大 |
| 夾臂 + L 形定位膠帶 | M36 的治具。DoF 從 ±40mm 縮到 ±20mm 後**不是可選項** |
| US$20–30 霧面 LED 補光板 | 為了能鎖 1/160s 曝光 |

## 6. 兩個零成本的降風險動作（審查建議，採納）

**① 內建計畫改用互不相鄰的腳位。**
原設計用 `GND_D / 5V / D7 / D8`——而**相鄰腳混淆正是現在最主要的失效模式**（半徑/腳距 = 1.56，同排兩側鄰居都在圈內）。改成例如 `GND_D / 5V / D10 / D2`，讓 demo 的每個目標腳位彼此相距數個腳距。**零成本，直接把最大的失效模式從 demo 路徑上移開。**

**② Beat 3 三級出貨**（見 §2.3）。把 Beat 3 的可演出性與精度波次的成敗解耦。

## 7. 風險

| 風險 | 對策 |
|---|---|
| **Beat 3 在 demo 當場打錯勾** | §2.3 三級出貨＋§6① 非相鄰腳位＋`verdict_dangerous_rate ≤0.01` 閘門；寧可多顯示 `uncertain` |
| **M33 進度落後但看不出來** | 它不產生畫面上的東西卻堵住三個里程碑。當關鍵路徑管，每日檢查指標模組的可執行性 |
| **相機架設漂移／反光** | 已實測反光時 ORB survivors 崩到 9–14（gate 25）。M36 治具不是可選項；demo 前必跑 px/mm 理智檢查 |
| **MSMF 相機層卡死** | 已把 Windows MVP 預設切到 `capture_api: dshow`；`msmf` 仍可明確覆寫。仍需在最終實機與目標 C920 上做一次冷啟動/長時間串流驗證 |
| **guidance 靜默失效** | `wire_trace.enabled: false` 時 `POST /api/guidance/step` 仍回 `ok:true` 但永不產生 verdict。列入 E 的前置檢查 |
| **golden-v1 統計功效不足** | 40 frames 撐不起 `≤0.01` 的聲稱。正式數字必須在完整 session（≈225 frames、n≥150 verdict）上量 |
| **範圍回蔓延** | §3 排除清單是防線：要加項目必須先指出砍掉哪一項 |

## 8. 這個 MVP 講的故事

**「把相機對著開發板，它就看得懂這塊板子、看得懂你的接線、一步一步教你接、接錯會告訴你錯在哪、不確定的時候會說不確定——而且整套跑在你自己的筆電上，不需要網路。」**

| 提案賣點 | demo 對應 |
|---|---|
| 零資料成本上新板卡（免訓練 CV + 一次性校正） | Beat 1 |
| 視覺驗證實體接線（差異化核心） | Beat 3 |
| 可信賴：會說不知道 | §4.3 誠實性閘門 |
| 全地端、可離線、隱私不出機器（AI PC 戰略） | Beat 5 |
